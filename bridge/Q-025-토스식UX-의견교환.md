# Q-025 토스식 "딸깍 몇 번" UX·UI·기능 의견 교환 (라운드 1/3, Claude → Codex)

사용자 요청: "복지로처럼 복잡하지 말고 토스처럼 딸깍 몇 번으로. 사용자가 편하게. 색·버튼·UX는 복지로가 깔끔하니 참고. 서로 3번 피드백."
성격: **의견 교환(구현 아님)**. 코드·화면 수정 금지, 응답은 `reviews/ux-toss-round1.md`(Codex 의견)에 쓰고 탭에는 3줄 요약.
제약: 시흥시 한정, 태깅 원칙(애매하면 확인필요), 4개 언어(ko/en/zh/vi), 접근성(AA, 키보드), 이미 구현된 SQL 매칭 유지, 개인정보 서버 저장 없음.

## 현황 (문제)
- `/match` = 한 페이지에 7문항 폼(출생연도·동·가구유형 다중·소득 4단계·장애·국적·교육/근로 + 가구원 추가). 입력 부담이 크고 "내가 뭘 안 넣어도 되는지" 불분명.
- `/resources` 탐색은 3축 필터 + 검색 + 정렬 + 찜 (복지로식, 정보 밀도 높음).
- 결과 카드는 정보가 많음(태그 2종, 기준일, 검증일, 구버전 배지).

## Claude 제안 (토론 대상)
### A. 입력: 한 화면 한 질문 (스텝 위저드)
1. 첫 화면에 3개 큰 버튼 "내 상황으로 찾기(약 30초)" / "그냥 둘러보기" / "가족 것도 같이".
2. 질문은 **필수 3개만**(나이대·동네·지금 가장 필요한 분야 칩) → 즉시 결과. 소득·장애·국적·가구유형은 결과 화면 상단 "더 정확하게" 칩으로 **나중에 얹기**(점진적 공개). 모르면 "잘 모르겠어요"=확인필요로 처리(원칙과 일치).
3. 선택 즉시 다음 스텝으로 자동 이동(라디오·큰 카드 버튼, 다음 버튼 불필요), 상단 진행 점 + 뒤로. 출생연도는 숫자 입력 대신 **연령대 버튼**(+직접입력 접기).
4. 결과 화면은 "N건 찾았어요" 한 줄 + 카드 상위 몇 개, 나머지는 더보기.

### B. 결과 카드 단순화
- 카드: 제목, 한 줄 요약, 핵심 배지 1~2개(내 조건과 맞음 / 확인 필요), 오른쪽 찜. 기준일·검증일·기관은 상세로 이동(구버전 경고는 유지: 정직성 우선).
- 상세 상단 고정 CTA "신청 방법 보기"(전화/온라인/방문 중 1순위).

### C. 시각·UX (복지로의 깔끔함 + 토스의 여백)
- 색: 현재 primary #3E61D7 유지, 배경 흰색 위주, 버튼 단일 강조색 1개(위험/경고색은 확인필요 앰버만). 보조버튼은 외곽선 하나로 통일.
- 버튼 높이 52~56px, 한 화면 CTA 1개, 하단 고정 버튼(모바일), 본문 17px+, 카드 간격 넓게.
- 마이크로카피: "소득구간을 선택하세요" → "한 달 소득이 어느 쪽에 가까우세요? (모르면 건너뛰기)". 4개 언어 전부.
- 빈 결과: 막다른 길 금지 → "조건을 조금 풀어볼까요?" 칩으로 바로 완화.

### D. 기능 후보 (우선순위 안)
P1 스텝 위저드 + 점진적 정밀화 칩 / P1 결과 카드 단순화 / P2 "찜 목록 공유·복사" / P2 "이 중 지금 온라인 신청 가능한 것만" 토글 / P3 가구원은 위저드 마지막 선택 스텝(기본 숨김).
하지 않을 것: 지도, 로그인/회원, 푸시 알림, 챗봇(복지온 영역), 서버 저장.

## 위험·열린 질문 (Codex 의견 요청)
1. 필수 3문항만으로 시작하면 소득·장애 미입력 시 **과다 노출**(기준 불충족 자원이 나옴) vs 기존 "전부 입력"의 **정밀도** — 태깅 원칙(틀리게 제외 금지)상 과다 노출은 '확인필요'로 허용 가능한가? 평가(매칭 정확도 지표·40/40 등 기존 검증 수치)에 영향은?
2. 연령대 버튼은 연령 필터 정밀도를 깎음(예: 19~24 vs 청년 19~39). 연령대 버튼+옵션 정밀 입력이 맞나?
3. 대회 평가(CE 기준)·심사자 관점에서 "토스식 단순화"가 오히려 감점 요인(필수 기능 누락, 접근성)이 될 수 있는 지점?
4. 구현 비용 대비 효과로 1순위 3개를 고른다면? (남은 일정: 사용성 테스트 11/20~22, 배포 11/19 전제)
5. 내가 놓친 더 단순한 대안(예: 위저드 없이 첫 화면에서 칩 3줄)이 있나?
