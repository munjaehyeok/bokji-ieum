# 단위 검증 실행 계획 — 매칭 SQL × 결정표 40케이스

전제: 구현 완료 후(3주차) 실행. 기대값은 `단위케이스.md`에 이미 고정되어 있음 — **실행 결과를 보고 기대값을 고치지 않는다.** 불일치 = 결함 보고(수정은 backend 담당, 가중치 조정으로 무마 금지, 결정표 기준으로 SQL 수정 지시).

## 1. 준비

```bash
mysql bokji < 검증/fixtures.sql
mysql bokji -e "SELECT COUNT(*) FROM resource WHERE resource_id BETWEEN 9000 AND 9099"  # = 19
```

- 실데이터와 섞여 있어도 무방: 모든 확인 쿼리를 `resource_id BETWEEN 9000 AND 9099`(또는 `name LIKE 'TEST-%'`)로 한정한다.
- 실행 대상 SQL: `resource-mapper.xml`의 findMatches 쿼리. MyBatis 밖에서 돌릴 수 있도록 바인딩 변수(#{age}, #{dong}, #{hhCsv}, #{incomeRank}, #{disability}, #{nationality}, #{ewCsv}, category=NULL)를 리터럴로 치환한 사본을 케이스별로 만든다(또는 테스트 컨트롤러/MatchService 직접 호출 + 로그 확인 — 어느 쪽이든 증거는 쿼리 결과 원문).

## 2. 케이스 실행 절차 (케이스당 3단계)

1. **입력 치환**: 단위케이스.md의 사용자 입력 → 바인딩 값. 변환 규칙:
   - birthYear → age = 2026 − birthYear, 미입력 → NULL
   - dong 모름 → NULL / household·eduWork: 빈 값(모름) → NULL, 해당없음 → 'NONE' (03 문서 보충 Q2 확정 규약)
   - incomeRank 모름 → 0 / disability 모름 → 'U'
2. **확인 쿼리 실행** (매칭 쿼리를 서브쿼리로 감싸 대상 자원만 추출):

```sql
SELECT resource_id, name, score, matched_csv, need_check_csv
FROM ( /* findMatches 본문, 바인딩 치환 */ ) m
WHERE m.resource_id IN (…이 케이스의 대상 fixture ID…);
```

3. **판정** — 아래 3개가 전부 맞아야 PASS:
   - **포함/제외**: 기대 '제외'면 행이 안 나와야 함, '포함'이면 나와야 함. 제외 기대 케이스(AGE-05/06, DONG-02, HH-02/03, INC-02~04의 불일치 칸, DIS-02, NAT-02, EW-02/04)는 행 부재가 곧 증거 — `0 rows` 출력을 그대로 기록.
   - **score**: 기대 점수와 정확히 일치 (확인필요는 0점 — 점수가 붙어 있으면 결함).
   - **태그**: matched_csv / need_check_csv가 기대 태그 집합과 일치(순서 무관, 집합 비교).

## 3. 실행 순서와 묶음

| 묶음 | 케이스 | 비고 |
|---|---|---|
| 1 | CMB-03 | **최우선** — 전 필드 모름인데 제외되면 false negative(설계 원칙 위반), 최우선 결함 |
| 2 | NAT-04 | K자원×외국인 제외 금지 — 두 번째 감시 지점 |
| 3 | INC-01~05 | 입력 5회 × 자원 9005~9008 동시 확인 = 20칸. 한 쿼리 결과에서 4행(또는 부재)을 한 번에 판정 |
| 4 | AGE-01~08, DONG, HH(HH-05 포함), DIS, NAT-01~03, EW-01~04 | 조건별 |
| 5 | INC-06~07, CMN-01~02, CMB-01~02 | 태그 병기/미병기·무관·점수 합산 |
| 6 | CMN-03 | SQL로는 data_base_date만 확인, 뱃지는 화면 검증(통합 테스트)으로 이관 |

CMB-01은 정렬 검증 겸용: 같은 쿼리 결과에서 9016(6점)이 9015(0점)보다 앞에 오는지 확인.

## 5. 정리

```sql
DELETE FROM resource WHERE resource_id BETWEEN 9000 AND 9099;
ALTER TABLE resource AUTO_INCREMENT = 745;  -- fixtures(9000번대)로 상승한 AUTO_INCREMENT 원복
```

테이블명은 전부 소문자 기준(설계 02 확정: 전 테이블 소문자, ADMIN → admin_user). 확인 쿼리도 소문자 `resource`로 작성한다.

시나리오 S1~S6 실행 전에 반드시 정리(TEST- 자원이 상위 5위를 오염시키지 않도록). 7주차 회귀 시 fixtures.sql 재적재 → 37케이스 재실행 → 정리, 동일 절차.
