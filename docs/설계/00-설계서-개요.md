## 설계 원칙 5가지

1. **규칙 기반, 생성형 AI 미사용** — 같은 조건이면 항상 같은 결과. 복지온(RAG 챗봇)과의 핵심 차별점이므로 끝까지 유지한다.
2. **매칭 엔진 = SQL 한 방** — 제외·점수·추천 이유 산출을 MyBatis 쿼리 하나로 처리한다(03 문서). 744건 규모에서 애플리케이션 레벨 매칭 로직은 과설계.
3. **틀리게 제외하지 않는다** — 판정이 애매하면 '불일치(제외)'가 아니라 '확인 필요(포함+표시)'로 처리한다. 복지 서비스에서 false negative(받을 수 있는데 안 보여줌)가 false positive보다 치명적.
4. **비회원 우선, 개인정보 최소** — 조건은 세션에만, 로그는 익명(연령은 10세 밴드), 회원은 선택 기능.
5. **이관 가능한 구조** — 관리자 화면·변경 이력·자료 기준일·출처가 시 담당 부서가 바로 넘겨받을 수 있는 형태여야 한다(정책활용가능성 20점의 실체).

**심사 코멘트 반영**: "새 앱 개발보다 기존 시흥시 앱 개선" — 복지이음은 복지온을 대체가 아닌 보완(복지온이 못 하는 자격 판정만 담당)으로 포지셔닝하고, 상세 화면에서 복지온·웰인포로 역연결한다. 발표·문서 전반에서 이 프레임을 유지할 것.
