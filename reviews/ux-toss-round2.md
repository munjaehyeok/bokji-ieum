# 토스식 UX 의견 교환 — 라운드 2

## A. 필수 4단계 + 언제든 결과 보기

**방향은 동의하되 ‘필수 4단계’라는 표현과 게이트는 수정하는 게 좋다.** 첫 실행에서 권장 순서(나이→동네→가구→소득)를 안내하되, 어디서든 ‘현재 조건으로 결과 보기’를 쓸 수 있고 각 값은 모름/건너뛰기가 가능해야 한다. 4개 답을 강제하면 딸깍 수를 줄이자는 취지와 맞지 않는다. 가구·소득은 민감한 정보이므로 질문 이유와 선택적 제공임을 밝혀야 한다. 장애·국적·교육/근로는 결과 정밀화에서 추가하고, 가구원은 기존처럼 명시적 추가 선택으로 둔다.

순서가 정확도에 미치는 영향은 입력 상태 그 자체보다 **미입력 처리와 조기 결과 전환의 구현**에 달려 있다. 같은 40개 고정 사례를 기존 흐름과 새 흐름에 입력해 결과 ID, `일치/확인필요` 라벨, 제외된 ID를 비교한다. 나이·동네 등 필터별로 모름/입력 조합을 나누어 결과 수와 확인필요 비율을 기록한다. 사용성 테스트에서는 어느 단계에서 멈추는지와 결과 진입률을 보되, 결과 건수가 많아진 것을 정확도 저하로 오판하지 않도록 기대 ID와 라벨 기준도 함께 둔다. 어떤 미입력도 기존 규칙과 다르게 탈락 조건으로 바뀌면 안 된다.

## B. 결과 조건 편집: 바텀시트 vs `/match` 재진입

**11/19 배포 전에는 기존 `/match` 재진입을 권한다.** 바텀시트는 짧아 보이지만 단계 복원, 포커스 트랩/복귀, 스크린리더 알림, 모바일 키보드와 화면 높이까지 새로 검증해야 한다. 기존 편집 경로를 사용하되 가능한 경우 마지막 입력 상태를 보존하고, 결과로 돌아왔을 때 결과 위치와 선택한 필터를 복원하는 편이 일정·접근성 위험이 낮다. 해당 보존이 이미 지원되지 않으면 우선 기존의 명확한 재입력 동작을 유지한다. 바텀시트는 사용성 테스트에서 전체 재진입의 반복 부담이 확인되고 별도 접근성 검증 시간을 확보한 뒤 후속으로 검토한다.

## C. 구현 슬라이스와 검증 순서

작업 착수 전 사람/구현자가 아래 합의와 입력 상태 전이를 계약으로 확정하고, 결과 ID/라벨 비교용 40개 사례를 기준선으로 고정한다. UI·JS 소유 경로가 겹치는 작업은 병렬화하지 않고 순차 진행한다.

1. **T0 — 동작 계약과 기준선:** 조건별 ‘모름/미입력’ 의미, 언제든 결과 보기, 이전/재진입 시 상태 보존, 카테고리가 자격조건이 아닌 결과 필터임을 명시한다. 검증은 기존 `match-regression.py`와 40개 사례의 ID·라벨 스냅샷 비교.
2. **T1 — 시작 경로:** 홈의 맞춤 찾기/둘러보기 두 CTA와 작은 가족 경로. 소유 경로: `WEB-INF/views/index.jsp`, 관련 `messages_*.properties`, 해당 홈 스타일. 검증: 4개 언어 문구, 390/1280px 캡처, 키보드 진입 및 두 경로의 URL/동작.
3. **T2 — 조기 결과가 가능한 위저드:** 단계 문구·진행 표시, 각 단계의 건너뛰기/이전, 결과 보기, 단일선택 자동 이동과 다중선택 명시적 다음. 소유 경로: `WEB-INF/views/match/form.jsp`, `static/js/bokji.js`, `static/css/bokji.css`, 메시지 리소스. T0·T1 이후 직렬. 검증: 모든 단계/모름 조합, 중간 결과와 최종 결과 ID·라벨 비교, 4개 언어·키보드/스크린리더 포커스·모션 감소·390px 스모크.
4. **T3 — 결과에서 조건 추가 및 카드 밀도 조정:** 기존 요약/편집 경로와 상태 복원, 카드의 핵심 문구와 세부정보 위계. 소유 경로: `WEB-INF/views/match/result.jsp`, 필요한 경우 결과 카드 뷰, 관련 JS/CSS 및 메시지. 검증: 선택 조건 보존, 카테고리 필터와 자격판정 구분, 날짜/오래된 자료 배지 존치, 비어 있는 결과의 수동 완화, 회귀·접근성·화면폭 스모크.

전체 폭이 좁으므로 T1·T2를 첫 사용자 테스트 전 최소 범위로 하고, 결과 카드 재배치는 수치·완주 문제를 확인한 뒤 진행하는 게 안전하다. 신규 SQL 매칭 동작이나 데이터 형식 변경은 이번 UX 작업에 포함하지 않는다.

## D. 추가 이득과 위험

토스식 단순화의 이득은 첫 행동을 분명히 하고, 모바일에서 한 번에 읽고 결정할 양을 줄이며, 복지 용어를 일상 언어로 바꾸는 데 있다. 심사에서도 꾸민 화면보다 **왜 이 결과가 나왔는지 설명하고 잘못된 배제를 방지하는 설계**가 차별점이 될 수 있다.

놓치기 쉬운 위험은 복잡성을 질문에서 결과 화면으로 옮기기만 하는 것이다. ‘N건 찾았어요’가 자격 확정처럼 읽히거나 확인필요가 작고 흐린 보조 배지로 내려가면 신뢰 문제가 생긴다. 결과 수를 늘리는 것을 성공으로 보상하면 무관한 자원까지 많아 보일 수 있다. 가족/소득 질문은 민감하므로 강요처럼 보이지 않아야 하며, 문항을 줄이면서 오래된 사업내용 경고·기관 확인 안내가 밀려나지 않도록 해야 한다. 큰 버튼과 자동 이동도 저시력/운동 제약 사용자에게 반드시 더 쉽지는 않으므로 4개 언어의 실제 글자 길이, 확대, 키보드와 스크린리더를 함께 본다.

## ④ 수정된 합의안 초안

1. 홈은 **내 조건으로 찾기**를 주 CTA, **복지자원 둘러보기**를 보조 CTA로 둔다. 가족 조건은 작은 선택 경로로 제공한다.
2. 맞춤 흐름은 한 화면 한 질문과 권장 순서(나이→동네→가구→소득)를 쓴다. 이 순서는 안내일 뿐 강제 관문이 아니다. 모든 단계에서 모름/건너뛰기, 이전, 현재 조건으로 결과 보기를 제공한다.
3. 나이는 큰 숫자 입력과 모름을 제공하고 연령대 대표값으로 대체하지 않는다. 가구·소득은 선택 목적을 알리고 건너뛸 수 있게 한다. 분야는 자격조건이 아닌 결과 필터에 둔다.
4. 단일선택 자동 이동은 테스트에서 오입력과 접근성 문제가 없을 때만 활성화하고, 다음 질문 제목으로 포커스 및 단계 안내를 전달한다. 다중선택은 명시적 다음을 쓴다.
5. 결과는 일치와 확인필요를 명확히 구분한다. 카드에서 기준일·오래된 자료 경고를 유지하고, 세부 정보는 상세에서 보여준다. 조건 편집은 우선 기존 `/match` 경로를 이용하고 상태 보존을 검증한다.
6. 실제 신청 수단이 확인된 경우에만 신청 CTA를 노출한다. 빈 결과 완화는 사용자가 직접 선택하게 한다. 로그인·서버 저장·지도·푸시·챗봇은 제외한다.
7. 배포 전 같은 40개 사례의 결과 ID/라벨, 4개 언어, AA 대비, 키보드/스크린리더, 확대, 모바일 폭과 핵심 사용자 흐름을 검증한다. 완료시간·중도 이탈·확인필요 이해도를 함께 측정하고 결과 건수 자체를 성공 지표로 삼지 않는다.
