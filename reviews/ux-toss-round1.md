# 토스식 UX 의견 교환 — 라운드 1

## ① 제안별 동의·반대

- **첫 화면에 ‘내 상황으로 찾기 / 둘러보기 / 가족 것도 같이’ 제공 — 동의:** 사용자가 원하는 시작점을 직접 고를 수 있고, 기존 둘러보기 경로도 보존한다. 가족 입력은 기본 경로에서 감추고 선택으로 둔다.
- **나이·동네·필요 분야만 먼저 묻고 나머지는 결과에서 추가 — 조건부 동의:** 시작 부담을 줄이는 방향은 좋다. 다만 나이/동네를 필수로 막으면 모르는 사용자에게 진입 장벽이 되고, 필요 분야는 자격조건이 아니라 분류 필터임을 구분해야 한다.
- **선택 즉시 다음 단계 이동 — 단일 선택에 한해 동의:** 빠르지만 오입력·키보드 사용자에게 놀라운 화면 전환이 될 수 있다. 자동 이동은 짧은 지연, 취소/뒤로 가기, 충분한 포커스 이동과 화면 읽기 안내가 있어야 한다. 다중 선택은 명시적 ‘다음’이 낫다.
- **연령대 버튼 — 현재 방식 그대로의 대체에는 반대:** 기존 매칭은 연령 숫자 기준이다. 연령대를 임의 대표 나이로 바꾸면 경계에서 잘못된 제외나 과도한 일치가 생긴다. 프리셋은 정확한 나이 입력을 채워 주거나 넓은 후보 탐색으로 쓰되 기준을 설명해야 한다.
- **결과 카드 축약 — 동의:** 목록에서는 제목·요약·일치/확인필요를 먼저 보여주고 세부는 상세로 옮긴다. 기준일 및 ‘2022 이전 자료’ 경고는 신뢰를 위해 목록에서도 남긴다.
- **상세 상단 신청 CTA — 조건부 동의:** 실제 신청 URL/전화/방문 정보가 확인된 경우에만 해당 방식으로 연결한다. 신청 링크가 없으면 ‘신청 방법 확인’처럼 실제 동작을 과장하지 않는 문구를 쓴다.
- **찜 공유/복사, 온라인 신청 가능 필터 — 후순위:** 저장/공유 방식, URL 정보 노출, 신청 가능 데이터의 최신성이 정해지지 않았다. 로그인·서버 저장 없이 가능한 범위와 개인정보 영향을 먼저 정의해야 한다.
- **경고색을 앰버 하나로 통일 — 동의:** 색만으로 상태를 구별하지 말고 ‘확인 필요’ 텍스트/아이콘도 함께 쓴다. 기존 경고 배지의 대비를 다시 확인한다.

## ② 열린 질문 답변

1. **과다 노출:** 모름/미입력을 이유로 자원을 제외하지 않는 것은 팀의 ‘틀리게 제외 금지’ 원칙과 맞는다. 단, 조건 미확인 상태의 후보에는 그 이유를 ‘확인 필요’로 표시하고, 확정 자격처럼 보이지 않게 해야 한다. 정확 일치와 미확인 후보를 분리하고 입력 전후 결과 수 및 사유를 확인한다. 기존 40/40 수치는 테스트 케이스의 기대 결과와 앱 결과를 다시 비교해야 기준선으로 쓸 수 있다. UI 개선을 이유로 기존 매칭 지표를 자동 승계하지 말고 같은 케이스를 재실행한다.
2. **연령대:** 첫 화면의 프리셋은 빠른 선택지로 제공하되 ‘직접 입력/모름’을 함께 둔다. 프리셋이 범위 매칭을 지원하지 않는 기존 API/SQL에 대표 연령 하나로 축약돼서는 안 된다. 범위 매칭 계약을 바꾸지 않는 단계에서는 정확한 연령을 선택한 뒤 결과를 좁히거나, 연령 미입력의 후보+확인필요 안내로 처리하는 편이 안전하다.
3. **평가·접근성 위험:** 필수 기능인 동·나이·가구원·조건을 숨기거나, 데이터 기준일/구버전 안내를 없애거나, 빠른 자동 이동으로 키보드·스크린리더 포커스를 잃게 하는 경우 감점과 사용성 저하 위험이 있다. 미입력 상태의 결과를 ‘지원 가능’으로 단정하는 것도 위험하다.
4. **우선순위 3개:** (1) 시작 화면에 ‘내 조건으로 찾기/둘러보기’ 두 경로와 선택적 가족 경로 제공, (2) 기존 입력을 유지하면서 단일 선택 단계의 문구·선택 카드·진행/건너뛰기 개선, (3) 결과 카드의 첫 화면 정보를 줄이되 일치/확인필요·기준일/구버전 배지·상세 연결을 유지. 세 번째까지는 기존 매칭 계약을 바꾸지 않는 범위에서 먼저 검증한다. 결과의 점진적 필터는 다음 순위다.
5. **더 단순한 대안:** 첫 화면에서 ‘내 상황으로 찾기’가 현재 흐름을 시작하고, 바로 아래에 ‘둘러보기’를 둔다. 탐색은 기존 목록을 열고, 맞춤 찾기는 질문을 하나씩 보여준다. 결과 상단에는 현재 입력 요약과 ‘조건 더하기’를 두어 나중에 정밀화한다. 시작부터 세 가지 질문을 한 화면에 압축하지 않아도 된다.

## ③ 수정 제안

- ‘약 30초’는 실제 사용성 테스트에서 확인되기 전에는 약속하지 말고 예상 시간 또는 단계 수를 표시한다.
- 건너뛰기는 항상 보이게 하고, 건너뛰면 제외 대신 ‘조건 미확인’으로 남긴다. 나이/동네도 모름을 허용한다.
- 단일선택 자동 이동은 사용성 테스트에서 오선택·뒤로 이동이 없는지 확인 후 적용한다. 기본적으로 키보드 포커스가 다음 질문 제목으로 이동하고 스크린리더가 단계 변경을 알리도록 한다. 모션 감소 설정을 존중한다.
- 결과 카드는 제목, 핵심 요약, `조건 일치` 또는 구체적인 `확인 필요`, 찜을 우선 노출한다. 기준일과 오래된 자료 배지는 유지하며, 기관·연락처·긴 본문은 상세에서 제공한다.
- 빈 결과에서는 자동으로 필터를 풀지 말고 사용자가 누를 수 있는 완화 칩을 제안한다. 완화 후 어떤 조건이 풀렸는지 알려준다.
- 매칭 정확성은 기존 테스트 케이스 동일 입력으로 전후 결과 ID·라벨을 비교한다. UX는 완료율, 완료시간, 건너뛰기/뒤로 비율, 결과 상세 진입률과 키보드/스크린리더 작업 성공률을 함께 본다.

## ④ 라운드 2 최종 합의안 초안

1. 홈에 기본 CTA ‘내 조건으로 찾기’, 보조 CTA ‘복지자원 둘러보기’를 제공한다. 가족 조건은 맞춤 흐름의 선택 단계로 둔다.
2. 맞춤 흐름은 한 화면 한 질문, 진행 표시, 이전/건너뛰기, 모름 선택을 제공한다. 임의 연령 대표값이나 새 SQL 매칭 규칙은 추가하지 않는다. 자동 이동은 단일선택에 한해 접근성·오입력 테스트를 통과한 경우에만 켠다.
3. 결과는 정확 일치/확인필요를 분명히 구별한다. 목록 카드는 핵심 정보만 먼저 보여주지만 기준일과 오래된 자료 경고는 남긴다. ‘조건 더하기’는 기존 입력을 보존하며 사용자가 직접 선택한다.
4. 신청 CTA는 확인된 연락처/URL만 연결하고, 없는 경우에는 신청 방법 확인을 담당 기관에 안내한다. 로그인, 서버 개인정보 저장, 지도, 푸시, 챗봇은 범위 밖으로 둔다.
5. 4개 언어, 키보드, 스크린리더, AA 대비, 모션 감소, 모바일 폭을 완료 기준에 포함한다. 사용성 테스트와 동일 입력 회귀 결과를 확인한 뒤 단계별로 합의한다.
