# R-002 응답 — 방향 정정 및 후속 구현 조건

검토일: 2026-10-19. 현재 AGENTS.md, BRIEF, R-002, 이전 지시서, REVIEW.md·REVIEW.standards.md, 매칭 설계·매퍼, API/Gov24 SQL, reliability-tagging.sql, 태깅 현황을 정적으로 대조했다. DB·테스트·브라우저는 실행하지 않았다. 구현 완료 승인이 아니라 질의 (a)~(c)에 대한 방향 결정이다.

## (a) P1-1: 기각 제안에 동의하되 사람 확인 필요

이전 Q-001에서 소득 순위 판정 전체를 금지한 판단을 정정한다. 현재 AGENTS.md 고정 규칙은 명시된 구간에만 income_rank를 허용하며, 매칭 설계 §3은 해당 순위의 가점·제외를 명시한다. resource-mapper.xml:47~50, :115~117은 그 계약을 따른다. 따라서 **순위 판정이 존재한다는 이유만으로 P1이라고 한 지적은 철회 제안**한다. 별도의 구체적 오제외 사례 없이 전체 소득 로직 제거를 요구하지 않는다.

Q-001의 T0·T1·T4와 금지사항 중 소득 점수·제외 제거 및 ‘소득 입력을 바꾸어도 집합·점수 불변’ 요구는 이 응답으로 대체한다. 기존 소득 결정표를 유지하고, 모름(0)은 제외하지 않으며 확인필요, 구간으로 환원할 수 없는 기준은 rank=NULL·income_uncertain='Y'로 처리하는 회귀 기준을 사용한다. 소득 조건 일치는 최종 수급 자격 확정을 의미하지 않는다.

AGENTS.md의 **‘P0·P1 기각은 사람 확인’** 규칙 때문에 이 건의 최종 종결은 사람 확인 후다. 이는 구현자에게 소득 로직 제거 작업을 계속하라는 뜻은 아니다. 사람 확인 자료에는 이전 지적, 현재 규칙·결정표, 이 정정 사유를 함께 제시한다.

추가 점검: docs/데이터/태깅-현황.md:63·80에는 아직 ‘180% → 가장 가까운 rank’ 서술이 있어 현재 AGENTS.md와 충돌한다. 과거 기록은 보존하고 현재 규칙과 구분하며, 실제 해당 행·생성기도 점검한다. 매퍼 :94~97의 INCOME_DETAIL은 rank IS NOT NULL을 요구하므로 **rank=NULL·uncertain=Y인 자원도 화면에서 확인필요가 전달되는지** 확인한다. NOTE로 전달되는지까지 보아야 하며, 이 정적 조건만으로 표시 누락을 확정하지 않는다.

## (b) 효도수당: age_min 해제 + 확인필요에 동의

api-update-20261014.sql:9의 원문은 ‘1세대가 만70세 이상인 3세대 가구’ 조건이다. 이를 단일 사용자 연령에 적용하면 가구원 조건과 입력자의 나이를 혼동한다. 현재 입력 계약에 해당 가구원의 나이를 별도로 받는 근거가 없으므로 **age_min=70을 해제하고 원문 및 가구·거주기간 조건을 확인필요로 남긴다.** 신청자의 법적 범위를 이번 검토에서 새로 확정한 것은 아니다.

집수리와 전동보장구 보험의 해제 방향도 타당하다. 현재 reliability-tagging.sql은 두 건만 처리하므로 효도수당을 추가해야 한다. 원문 보존, 안정적인 대상 식별, 재실행 시 note 중복·추가 변경 없음이 필요하다. 확인필요 문구는 ‘어느 한 조건이면 수급 확정’처럼 쓰지 말고 ‘대상에 OR 조건이 있어 개별 확인 필요’로 한정한다. 거주·보장구 등 다른 요건도 남아 있다.

검증 기준: 다른 입력은 제외되지 않게 고정하고, 젊은 수급자의 집수리, 65세 미만 장애인 및 65세 이상 비장애인의 보험, 70세 미만 가구원의 효도수당이 해당 연령·장애 태그 때문에 제외되지 않는지 확인한다. 각 결과에 확인필요가 표시되어야 한다. 진짜 전체 연령 제한과 ±1세 관용은 유지한다. 신규 48건 점검이 기존 744건 전체의 안전성을 입증하지는 않는다.

## (c) P1-3: 최소안을 선택, 별도 컬럼은 이번 필수 범위에서 제외

**본문 미대조 매칭 건의 data_base_date를 근거가 있는 본문 기준일로 복원하고, 확인 이력은 last_verified_date와 근거 대장에 범위를 밝혀 남긴다.** 별도 본문확인일 컬럼은 T0 필수사항으로 요구하지 않는다. Q-001 T2의 ‘확인 범위 구분’ 수용기준은 유지한다.

- 복원 대상은 UPDATE 문 수가 아니라 중복 제거한 resource_id별 변경 이력으로 확정한다. API 신규 행을 Gov24가 다시 갱신한 경우도 있으므로 모두 2022로 일괄 복원하지 않는다. seed·각 적재 단계·본문 출처를 대조해 직전의 정당한 기준일을 복원하고, 근거가 없으면 미확인으로 둔다.
- last_verified_date는 본문 확인일로 표시·정렬하지 않는다. 시설 주소·전화 대조, 목록 매칭, 사업내용 대조를 대장에서 구분하고, 카드·상세·AJAX·4개 언어에는 보수적으로 확인 범위를 표시한다. 스키마 추가 없이도 가능한 표현으로 T0를 작성한다.
- 자원 315는 동일 사업 여부가 불확실하다. ‘추가형’과의 동일성 확인 전에는 해당 매칭을 존속 확인 근거로도 승격하지 않는다. 수집 이력은 남기되 미확인임을 명시한다.
- 원천 수정일은 수록 본문의 완전한 검증일이 아니다. 날짜 복원 후에도 부분 확인을 전체 확인으로 보이게 하지 않도록 배지·정렬 설명을 점검한다. 새 API 본문 수록도 모든 필드의 교차 검증 완료와 구분한다.
