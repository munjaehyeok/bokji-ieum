대상: `main...422de7c7aabec6f92bdbf2d11faebc7706d5b9cc` 및 제출된 현재 파일. 이번 승인은 T1/T2 보정 슬라이스를 대상으로 판단하며, 미착수 T3~T6를 완료했다고 요구하지 않는다. 작업 트리의 미커밋 bridge/tab.sh와 R-003은 커밋 diff와 구분했다.

## 지적

### [P1] src/main/resources/sql/reliability-provenance.sql:4
Axis: Correctness

Problem: 복원 SQL이 알려진 잘못된 상향값만 대상으로 하지 않아, 이후 정당한 최신화까지 다시 과거로 되돌린다. :20의 확인일 제거도 같은 문제다.

Evidence: :4~19는 `data_base_date > 복원값`이면 무조건 복원한다. 예를 들어 id=15의 본문을 실제 대조해 기준일을 2026-10-20로 갱신한 뒤 이 SQL을 재실행하면 2022-12-31로 내려간다. id=315가 동일 사업으로 확인되어 새 last_verified_date를 얻어도 :20은 다시 NULL로 만든다. 동일 데이터에 연속 2회 적용하는 현재 테스트로는 이 후속 변경 훼손을 잡지 못한다. README·SETUP은 이 SQL을 적재 절차로 제공하고 있다.

Suggested direction: 근거 대장에 잘못된 변경 전 값과 복원 후 값을 기록하고, 알려진 잘못된 상태에만 보정이 적용되도록 제한한다. 315 확인일 제거도 해당 목록 매칭으로 생긴 상태에 한정한다. 이후 정상 본문·확인 이력을 가진 행은 보존한다.

Verification: static + reasoning. 최초 보정·즉시 재실행·정상 최신화 후 재실행의 세 상태로 검증 필요.

### [P2] docs/검증/data-gate.sh:19

Evidence: 양변은 모두 resource 테이블의 국적 조건만 센다. 다른 태그 때문에 매퍼가 모름 입력 자원을 잘못 제외하더라도 양변은 같을 수 있다. 이 검사는 국적별 분할 확인이며 resource-mapper의 judgeWhere를 실행하지 않는다. R-003이 한계를 밝힌 것은 적절하지만 SPEC의 완료 표시와 게이트 이름은 실제 검증 범위를 넘어선다. :26의 활성 792·F전용 23 등도 출력일 뿐 단언이 아니다.

Suggested direction: 현재 검사를 데이터 분할 검사로 명명하고, 모름 입력의 실제 매퍼 결과 집합을 같은 DB의 활성 전체−F전용 집합과 비교하는 검증을 추가한다. 태그 해제 3건도 실제 매칭 결과와 확인필요 태그를 확인한다. 의도한 고정 스냅샷 수치는 별도 단언으로 보호한다.

Verification: static. 현재 단언이 앱 노출 불변식을 입증하지 못함을 확인.

## 수용한 부분과 범위

- 집수리·보험·효도수당의 태그 해제 및 원문 보존 방향은 타당하다. 태그가 남아 있을 때만 메모를 추가하는 조건은 즉시 재실행 중복을 방지한다.
- 기준일 CSV는 seed 유래 7건과 API 본문 유래 9건을 구분한다. 758을 2025-05-31로 복원하고 66·67의 API 단계 상향까지 포함한 방향도 타당하다. 다만 정확한 최종 행별 값은 DB 실행 증거로 확정해야 한다.
- UI 소스 변경은 없으므로 이번 슬라이스만을 위해 신규 화면 구현을 요구하지 않는다. 데이터 변경으로 배지·정렬이 영향을 받으므로 통합 승인 전 실제 화면 확인은 필요하다.
- 보험 메모의 ‘어느 한쪽만 충족해도 해당’은 개별 조건 확인으로 표현을 한정하는 편이 정확하다. 이를 사업 전체의 수급 확정으로 해석하지 않도록 T3 문구에서 정리한다.

## 우선순위 지시

1. 이번 P1 두 건과 실제 매퍼 회귀 증거를 보완한 뒤 보정 슬라이스를 재제출한다. 기존 PLAN의 T2가 담당할 수 있으며, T3 착수 전 최소 매칭 회귀 기준을 확보한다.
2. **INCOME_DETAIL은 T3와 함께 배포 전 필수로 점검한다.** rank=NULL·uncertain=Y이면 현재 매퍼 :92~94에서 INCOME_DETAIL이 나오지 않는 것은 확인했다. 다만 NOTE→번역 라벨→초기 JSP/AJAX로 확인필요를 전달하는 경로가 있으므로, 표시 누락을 일괄 확정하지 않는다. 해당 전체 행의 NOTE 존재와 실제 표시를 검사하고 누락 사례만 수정한다. 소득 점수·제외 전체를 제거하지 않는다.
3. **180% rank는 T3 이전의 작은 데이터 점검으로 둔다.** seed id=269는 실제 rank=4·uncertain=Y다. 현 매퍼상 0~4 입력에서 rank 4가 소득만으로 제외시키지는 않지만, ‘구간 외는 rank 비움’ 규칙에는 맞지 않으며 입력 1~3에 가점·일치가 생긴다. 전체 해당 후보를 점검해 후속 SQL로 보정하고 원본 seed는 보존한다.
4. **기존 744건 전량 재검토를 T3 착수의 선행조건으로 만들지 않는다.** 배포 전에는 기존 태깅 근거가 불명확한 연령·OR·가구원 조건을 위험 목록으로 추려 점검한다. 시연 및 긴급·현금·주거 항목과 실제 오제외가 확인된 사례는 필수다. 나머지는 T5 대장에 확인·미확인으로 구분한다. 전량 안전성 주장은 금지한다.
5. T5 착수 전에 독립 검증 작업을 PLAN에 추가한다. 현재 plan-check의 경고를 완료 기준으로 오인하지 않는다. 데이터 게이트의 셸 오류 처리도 exit code를 보존하도록 강화한다(:7 파이프는 mysql 종료코드를 숨기며 :12 DB 초기화 성공을 확인하지 않는다).
