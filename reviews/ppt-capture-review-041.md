## 3. SQL 요약과 실제 코드 대조: 문제

### [P1] 17쪽 Picture 25의 연령 SQL — 연령 모름 허용 분기 누락

Axis: Spec / Correctness

Problem: 그림은 `NULL(조건 없음)·모름은 제외하지 않고`라고 설명하면서, 연령 부분에 자원 조건이 NULL인지와 입력 연령 비교만 남겼다. 입력 연령 자체가 NULL인 경우를 허용하는 실제 코드의 바깥 분기가 없다. 따라서 그림의 식을 그대로 해석하면 모름 입력에서 연령 조건 자원을 제외한다.

Evidence:

- 실제 `src/main/resources/mappers/resource-mapper.xml:119`는 입력 연령 NULL을 먼저 허용하고, 값이 있을 때만 최솟값/최댓값 ±1 비교를 적용한다(`:119~121`).
- 새 PNG의 두 연령 줄에는 그 입력 NULL 우회 분기가 없다.
- 예: 자원 599의 `age_min=60`, `age_max=NULL`에 입력 연령 NULL을 적용하면 아래와 같다. SQL 비교의 NULL 결과는 WHERE에서 통과가 아니다.

| 입력 연령 | 실제 연령식 결과 | PNG 요약 연령식 결과 | 노출 |
| --- | --- | --- | --- |
| NULL | TRUE | NULL | 실제 통과 / 요약 제외 |
| 58 | FALSE | FALSE | 둘 다 제외 |
| 59 | TRUE | TRUE | 둘 다 통과(경계 관용) |
| 60·71 | TRUE | TRUE | 둘 다 통과 |

읽기 전용으로 Python sqlite3의 메모리 연결에서 두 식의 NULL 논리를 계산해 위 차이를 재현했다. MySQL 통합 테스트를 실행했다는 의미는 아니다. 이 사례의 `NULL >= 59`와 WHERE 통과 여부 차이는 SQL의 NULL 논리에 따른다.

Suggested direction: 그림에 실제 연령 모름 우회 조건을 보존한다. 또는 구체 SQL 대신 모름/경계/불일치를 구분하는 정확한 의사코드로 바꾼다. `발췌·요약` 표시는 가능하지만 핵심 “모름을 잘못 제외하지 않음” 규칙의 의미까지 바꾸는 생략은 피해야 한다. 제품 코드를 수정할 사안은 아니다.

Verification: static + 메모리 SQL 진리값 비교

### 나머지 SQL·범례

- **동 조건:** `NULL` 자원/입력 허용과 `FIND_IN_SET`은 실제 `:122~123`과 의미가 맞는다.
- **가구:** 실제 `:124~127`은 모름이면 해당 필터를 생략하고, 해당 없음이면 제약 자원을 제외하며, 선택값이면 교집합을 검사한다. PNG의 `NULL OR 교집합`은 선택값이 있는 경우의 요약으로는 가능하다. 위 P1 수정 때 가구의 모름/해당 없음 분기도 설명하거나 “선택값 있는 경우 발췌”라고 전제를 명시하면 된다.
- **소득:** PNG는 WHERE의 NULL/입력 0/등급 비교를 보여준다. 생략한 `입력=4 AND 자원=4` 절은 이 WHERE 안에서는 이미 `4<=4`에 포함돼 있으므로 이번 생략 자체가 노출 결과를 바꾸지는 않는다. 다만 일치/확인 필요의 구분은 별도의 `judgeCols`에 있다(`:80~82`, `:101~106`). 이 요약 WHERE가 세 상태 판정 전체를 산출하는 코드라고 설명하면 안 된다.
- **장애:** PNG의 조건은 실제 `:131`과 맞는다.
- **MatchService:** 실제 SQL 호출은 `MatchService.java:39`, 상세 판정 호출은 `:51`이며 서비스는 라벨 변환과 결과 순서 정리를 수행한다. “SQL 규칙으로 판정”이라는 역할 설명은 맞는다.
- **소득 범례:** 자원 rank의 통상 구간을 설명한 것으로 읽으면 되지만 4에는 중위 180% 상한 자원도 `income_uncertain=Y`와 함께 들어간다. 실제 표의 181·213이 그 예다. `4=중위150%`가 모든 해당 행의 실제 상한이라는 뜻으로 읽히지 않게 `4는 범위 밖 상한도 Y와 함께 저장, 원문 확인` 정도를 덧붙이는 편이 정확하다. 사용자 입력 4의 라벨은 `그 이상`이므로 자원 등급과 구분한다.
- `‘-’=조건 없음(NULL)`은 **해당 필드**에서 제외 조건이 없다는 뜻이다. 행 전체의 자격이 누구에게나 맞는다는 뜻은 아니다. `‘확인’ Y`의 실제 필드명은 `income_uncertain`임을 표시하면 범위가 명확해진다.

## 5. 복지온 캡처 재사용·출처 위험

**출처 표기는 개선됐지만, 공개 페이지라는 이유만으로 자유 재사용이 확인된 것은 아니다.** 시흥시 정책은 자료별 공공누리 표시·유형을 확인하고 기관명/URL 등 출처를 표시하도록 안내하며, 표시 없는 자료는 담당 부서와 협의하도록 안내한다. 이번에 확인한 정책 페이지 자신의 공공누리 표시를 챗봇 UI 전체의 이용허락으로 확장할 수는 없다. [시흥시 저작권 정책](https://www.siheung.go.kr/main/contents.do?mId=0310000000)

교육·비평 목적의 필요한 부분 인용에는 저작권법 제28조의 근거가 있지만 정당한 범위와 공정한 관행 등 요건이 따른다. 출처 표시만으로 모든 이용이 자동 허용되는 것은 아니다. 현 자료는 비교·비평을 위한 질문/답변 일부와 출처·날짜를 제시한다는 점에서 인용 목적을 설명할 여지는 있으나, 권리관계와 개별 조건을 확인하지 못했으므로 적법성을 확정하지 않는다. [저작권법 제28조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1033063671), [정부 생활법령의 인용·출처 안내](https://www.easylaw.go.kr/CSP/CnpClsMain.laf?ccfNo=3&cciNo=2&cnpClsNo=2&csmSeq=695&menuType=cnpcls&popMenu=ov)

실무상 출처를 `시흥시 시흥복지온`으로 명확히 하고, **`화면 일부 발췌·확대, 빨간 ①은 발표자 주석`**임을 표시하는 것이 좋다. 답변 원문은 바꾸지 않고 평가·집계와 분리한다. 유튜브 게시 등 대외 배포 단계에서는 해당 UI의 이용조건/권리 확인 또는 인용 요건 검토를 별도로 완료해야 한다. 현재 캡처에 명백한 권리 침해가 있다고 단정하거나, 검토를 위해 시흥시에 연락·사용허락 요청을 실행한 것은 아니다.
